## Why 78, not 222

The 222 items are not uniform. Batch 1 (dashboards/charts/cards) and Batch 2
(dead-credit) were the two categories where a single, reusable piece of
engineering genuinely resolved many registry entries at once — 59 items
share one 6-function backend module, 20 items share one generic adapter. The
remaining 144 are individual ERPNext document actions spread across ~80
distinct (doctype, action) pairs, each requiring its own source-verification
against the real ERPNext controller before any code is written (per this
project's own standing rule: no guessed method names, no generic RPC
backdoor, one fixed-purpose adapter per action). That is real, one-at-a-time
engineering work, not a batchable pattern — genuinely too large to complete
honestly in a single pass without degrading the verification rigor every
prior batch in this project has held to.

## What was completed (78 items, 2 commits)

### Batch 1 — All 59 required dashboards, charts and number cards
`erpnext:dashboard-chart:*` (28), `erpnext:number-card:*` (25),
`erpnext:dashboard:*` (6) — **100% of this category, 0 remaining.**

New file `my_store_ui/module_dashboards.py`: six real, permission-checked,
live-data functions (`get_accounts_dashboard`, `get_payments_dashboard`,
`get_buying_dashboard`, `get_crm_dashboard`, `get_selling_dashboard`,
`get_stock_dashboard`) computing every required metric from real ERPNext
data — `frappe.get_list()`/`frappe.db.count()`, `frappe.has_permission()`
gating every query, zero raw SQL, zero `ignore_permissions`. Ageing charts
bucket the real `outstanding_amount` field by document age. Profit and Loss
and Budget Variance reuse the standard "Profit and Loss Statement" and
"Budget Variance Report" query reports (`frappe.desk.query_report.run`,
the same reuse pattern already established for Gross Profit) instead of
reimplementing accounting logic. All six verified against real site1 data
via `bench execute` — see the actual returned JSON in the commit message of
`55a4d3e`.

Wired into `ModuleDashboardPage.vue` (routes `/finance`, `/purchases`,
`/crm`, `/sales`, `/inventory`) via `frontend/src/services/
moduleDashboards.js`, rendering through the existing `SmjKpiCard`/
`SmjChartCard`/`SmjBarChart`/`SmjDonutChart`/`SmjLineChart` framework with
loading/empty/error states and a manual refresh control.

Credited in the registry via a new `DASHBOARD_ANALYTICS_ADAPTERS` table
(`my_store_ui/audit/parity_registry.py`), matched by the scanner's exact
`(feature_type, name)` key — not a route guess, not a renamed capability.

**10 regression tests** (`my_store_ui/tests/test_module_dashboards.py`), all
passing against live site1 data.

### Batch 2 — Dead-credit: generic dashboard connections + a real bug fix
20 of the remaining 163 items after Batch 1 turned out to be ERPNext's
standard "Connections" sidebar tiles (e.g. Purchase Invoice → its source
Purchase Order), not distinct JS button actions. This was verified
precisely — not guessed — by loading each doctype's own real
`get_dashboard_data()` and checking whether the scanner's action key
matches a linked-doctype name in its `transactions`/`internal_links`
groups. 19 of the 20 were successfully credited (the 20th, Blanket
Order → Sales Order, stays pending because Blanket Order itself has no
Retail ERP route yet — the connection code is ready for when it does).

New generic adapter `get_dashboard_connections(feature, name)` in
`my_store_ui/universal/api.py`: reads each doctype's own dashboard config
(never hardcoded per doctype), resolves both external links (query by
fieldname) and internal links (child-table references), verifies every
returned name still exists and is still readable, and only surfaces linked
doctypes this app actually routes to — stricter than the standard
`frappe.desk.notifications.get_open_count`, which does not permission-filter
linked doctypes. Verified against real site1 data (Purchase Invoice
correctly shows its source PO; Supplier correctly shows 4 real POs and 2
real PIs with working routes). Wired into `UniversalDetailPage.vue` (the
actual page serving these doctypes — confirmed via the router, not assumed)
as a new "Linked documents" section.

**Also fixed a real, separate bug found while editing this file**: two
`"Supplier"` keys existed in the same `DOCTYPE_SPECIFIC_ACTIONS` dict
literal. Python silently lets the second occurrence win, so `hold`/`resume`
were never actually being checked even though the code intended to credit
them. Merged into one entry — see
[DEAD_CREDIT_FINAL_AUDIT.md](DEAD_CREDIT_FINAL_AUDIT.md).

**6 regression tests** (`my_store_ui/tests/test_dashboard_connections.py`),
all passing against live site1 data.
